## 원인 분석

- **직접 원인**: Toss Payments confirm API 의 게이트웨이 장애 (외부)
- **간접 원인 / 우리 시스템의 한계**:
  - 자동 재시도 횟수가 3회로 짧음 → 외부 장기 장애에는 무력
  - 사용자 응답에 "잠시 후 다시 시도" 가 친절하지 않음 → "재시도" 버튼 노출 불가

## 영향 정량화

- 결제 시도 실패: 5건
- 환불 필요한 중복 결제: 0건 (멱등성 정책으로 방지됨, prepare 단계 멈춤)
- 데이터 불정합: 없음 (모든 실패 주문이 `pending` 상태로 남음 → 30분 후 cron 이 `expired` 처리)

## 자동 복구 동작 확인

- 외부 복구 직후 사용자가 재시도 → 같은 `paymentKey` (없음 — Toss confirm 진입 전이므로) / 새 prepare 진입 → 정상
- 멱등성 테이블에 잘못된 `completed` 데이터 없음
- job_runs 의 `expire-stale-pending-payments` 가 정상 동작해 `pending` → `expired` 전환됨

## 배운 점

- 외부 장애 시 우리 자동 보호장치(멱등성/스케줄러)는 기대대로 동작했다.
- 그러나 **사용자 가시성**(친절한 에러, 재시도 UI)이 부족해 CS 문의가 발생함.
- 모니터링은 메트릭 수치는 보지만, "외부 의존성 상태" 자체는 별도 채널로 끌어와야 더 빠른 인지가 가능.
